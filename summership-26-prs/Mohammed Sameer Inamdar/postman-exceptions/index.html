A PyBe Story Module

The Postman's Route

Every day, Ramesh delivers 40 letters. Most days go fine.
Some days, something goes wrong at a specific door.
This is a story about what a good postman — and good code — does next.

Concept: Exception Handling · try / except / finally / raise

Stop 1

An ordinary delivery

Ramesh reaches 14 Lotus Lane. Gate's open. Letterbox is right there. He slips the letter in, marks it delivered, and moves on.

Nothing unusual happened here. In code, we'd call this the path we hope for, every time.

What this looks like in Python
try:
    deliver_letter("14 Lotus Lane")
    mark_delivered("14 Lotus Lane")

The try block is Ramesh just... doing his job. No problems expected — yet.

Stop 2

A locked gate

At 27 Banyan Road, the gate is padlocked. No one's home. Ramesh doesn't panic, and he doesn't just leave. He knows exactly what to do for this specific problem: slide the letter under the gap, note it as "left at gate."

What should code do when it hits a problem it already expects and knows how to handle?

What this looks like in Python
try:
    deliver_letter("27 Banyan Road")
except GateLockedError:
    leave_at_gate("27 Banyan Road")

except catches one named kind of problem — a locked gate — and gives Ramesh a specific, ready plan for it.

Stop 3

Two different doors, two different problems

At 9 Peepal Street, the house number doesn't exist anymore — renumbered last year. Different problem, different plan: he checks his revised list and redirects to 9B.

A locked gate and a wrong address aren't the same problem. They need different responses — and Ramesh's brain (like good code) handles each one on its own terms.

What this looks like in Python
try:
    deliver_letter("9 Peepal Street")
except GateLockedError:
    leave_at_gate("9 Peepal Street")
except AddressNotFoundError:
    redirect_to_updated_address("9 Peepal Street")

Multiple except blocks let one try handle several different, specific kinds of trouble — each with its own fix.

Stop 4

The logbook, no matter what

Good day or bad, easy street or a locked gate — at the end of every single stop, Ramesh writes the time in his logbook. Always. Whether the letter got delivered, redirected, or left at a gate, the log entry happens no matter which of those was true.

What Python keyword runs code no matter what happened — success or failure?

What this looks like in Python
try:
    deliver_letter("27 Banyan Road")
except GateLockedError:
    leave_at_gate("27 Banyan Road")
finally:
    log_timestamp("27 Banyan Road")

finally always runs — whether the try succeeded or an except caught something.

Stop 5

When Ramesh refuses to guess

At the last stop, the address on the envelope is smudged into nonsense — not a locked gate, not a known renumbering, just unreadable. Ramesh doesn't invent an answer. He flags it and sends it back to the sorting office with a clear note: "cannot deliver — address unreadable."

Sometimes the right move for code isn't to quietly patch things up. It's to stop and say exactly what's wrong, loudly, so a human can look at it.

What this looks like in Python
def deliver_letter(address):
    if not is_readable(address):
        raise ValueError("Address unreadable — cannot deliver")
    ...

raise deliberately signals a problem outward — this is not something to quietly work around.

Stop 6

The whole route, in code

Here's Ramesh's entire stop, start to finish — the plan for the expected, the safety net for the specific, the log that always runs, and the honest refusal when something can't be guessed.

The complete pattern
def handle_stop(address):
    try:
        if not is_readable(address):
            raise ValueError("Address unreadable — cannot deliver")
        deliver_letter(address)
        mark_delivered(address)
    except GateLockedError:
        leave_at_gate(address)
    except AddressNotFoundError:
        redirect_to_updated_address(address)
    finally:
        log_timestamp(address)

Quick check

1. If a letter delivers with no problems, does finally still run?

2. Why does Ramesh use two separate except blocks instead of one?

3. When should code use raise instead of quietly handling a problem?
