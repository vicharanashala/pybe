# 00 – Project Charter

## 1. Executive Summary
CKLIS is an educational intelligence framework for generating high-quality programming education through structured reasoning rather than direct content generation. It treats lesson creation as an engineering problem, not a prompt engineering problem. CKLIS is intentionally model-agnostic.

## 2. Problem Statement
Most AI-generated educational content suffers from:
- Teaching syntax before understanding
- Using analogies that entertain but do not explain mechanisms
- Producing inconsistent learning experiences
- Ignoring common beginner misconceptions
- Optimizing for engagement rather than comprehension
- Lacking a repeatable instructional methodology
- Depending heavily on a specific AI model

## 3. Vision & Mission
To establish a reusable, extensible, and model-independent educational framework that enables AI systems to consistently generate programming education centered on understanding, curiosity, and transferable mental models.

The AI system must: identify what learners misunderstand, build accurate mental models, select the most effective teaching scenarios, explain programming through observable mechanisms, generate technically correct content, evaluate educational quality, and evolve continuously.

## 4. Project Objectives
- O1: Improve Understanding — Prioritize conceptual understanding over memorization
- O2: Standardize Educational Reasoning — Repeatable reasoning independent of AI model
- O3: Reduce Beginner Confusion — Explicitly address misconceptions before introducing code
- O4: Maximize Knowledge Transfer — Teach reusable mental models, not isolated facts
- O5: Maintain Technical Accuracy — Every explanation consistent with accepted programming principles
- O6: Support Long-Term Evolution — Allow future extensions without redesigning the core

## 5. Guiding Philosophy
Learners remember experiences longer than explanations, mechanisms longer than analogies, and understanding longer than syntax. Programming should be taught by revealing HOW a mechanism works, not merely HOW code is written.

Educational sequence: Experience → Observation → Pattern → Mental Model → Programming Concept → Code → Application → Reflection

## 6. Design Principles
- P1: Education Before Entertainment — Learning outcomes take priority over engagement metrics
- P2: Scenario Before Syntax — Learners first understand the motivating situation
- P3: Mechanism Before Analogy — Analogies useful only after the mechanism is understood
- P4: One Primary Learning Objective — Each lesson focuses on a single dominant objective
- P5: Misconception First — Identify likely misconceptions before selecting a teaching strategy
- P6: AI Reasons Before Generating — Content generation is the final step
- P7: Technical Correctness — Simplification must never introduce incorrect concepts
- P8: Cultural Respect — Examples remain respectful, inclusive, and culturally appropriate
- P9: Explainability — Every educational decision should be traceable
- P10: Reusability — Components reusable across languages, formats, and platforms

## 7. Decision Framework (Priority Order)
When multiple educational approaches appear valid, evaluate by:
1. Educational effectiveness
2. Mechanism clarity
3. Mental model quality
4. Beginner familiarity
5. Cultural accessibility
6. Technical accuracy
7. Simplicity
8. Production efficiency

## 8. Core Terminology
- Learning Objective: The single primary outcome a learner should achieve
- Misconception: An incorrect or incomplete mental model commonly held by learners
- Mental Model: An internal conceptual representation explaining how something works
- Scenario: A real-world, fictional, historical, or abstract situation used to introduce a concept
- Pattern: The recurring mechanism extracted from a scenario
- Programming Concept: The computing principle being taught (e.g., loops, variables, functions)
- Episode: A complete educational lesson generated by CKLIS
- Engine: A specification module responsible for one stage of educational reasoning

## 9. Engineering Principles
- E1: Separate educational reasoning from content generation
- E2: Separate architecture from implementation
- E3: Prefer modularity over monolithic specifications
- E4: Prefer explicit reasoning over implicit assumptions
- E5: Every important concept should have one authoritative definition
- E6: Every specification should be understandable without external context
- E7: Avoid duplicated responsibilities
- E8: Optimize for long-term maintainability rather than short-term convenience

## 10. Core Educational Progression
Every lesson: Problem → Observation → Mechanism → Mental Model → Programming Concept → Code → Practice → Reflection
No module may violate this learning order unless a specification explicitly defines an approved exception.
